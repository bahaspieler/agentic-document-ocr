# Run Records

Every job the engine executes leaves one queryable row in Azure Table Storage. A single plugin call
gets its own row; a workflow gets one row carrying its step trace as JSON, not a row per step.

Recording lives in the `OcrAgent` core, so the CLI, the chat agent, and the MCP server are all
recorded the same way and the `Source` column says which one it was.

## Two recording points

A workflow drives its steps through the same tool bindings a direct call uses, so a single
interceptor would either lose workflow context or produce a row per step.

```
CLI / chat / MCP
       |
       v
decorated AIFunction surface
       |                    \
       | standalone call     \ RunWorkflow
       v                      v
RecordingAIFunction     WorkflowRunner.RunAsync
       |                      |
       |  one row             |  one row from WorkflowRunResult
       +----------> IRunStore <+
                        |
                        v
              Azure Table: OcrRuns
```

`WorkflowRunner` builds its record from the typed `WorkflowRunResult`, so no output is parsed back
out of strings. It also enters an ambient `RunScope` for the duration of the run, and
`RecordingAIFunction` no-ops while a scope is active, which is what keeps a twelve-step workflow at
one row. The scope tracks depth in an `AsyncLocal`, so concurrent MCP sessions cannot suppress each
other.

`RecordingAIFunction` derives from `DelegatingAIFunction` and leaves the inner name, description, and
JSON schema untouched, so the tool surface a model sees is unchanged. It skips `RunWorkflow`, which
the runner records itself, and the read-only `ListWorkflows`, `GetRun`, and `ListRuns`.

## Grouping the jobs one request produced

One natural-language request can become several jobs, because the model decides how many tools to
call. `AgentService` puts the conversation id on the same `RunScope` for the duration of a turn, and
both recording points read it from there, so the rows can be tied back together afterwards without any
tool or workflow signature mentioning a conversation. A direct tool call, a CLI invocation, or an MCP
client calling a tool itself leaves the column empty: nothing raised those on behalf of a conversation.

A failed write is logged and dropped. Bookkeeping can never fail a job that produced its output, and
leaving `Runs:Provider` at `none` gives a fully working engine with no history.

## Run IDs and row keys

Run IDs are RFC 9562 UUIDv7 values generated by `RunId`. The implementation remains compatible
with the guarded `net8.0` rollback target and mints the same identifier shape on both targets. A
counter in the `rand_a` field keeps ids created in the same millisecond strictly ordered.

Because the timestamp is readable back out of an id, the row key is
`{ticksDescending:D19}_{runId}`. Table Storage sorts row keys ascending, so listing returns newest
first with no sort, while `GetRun` stays a point read because the key is derivable from the id
alone. No secondary index, no partition scan. `PartitionKey` is the configured `GroupId`.

## Record shape

| Column | Notes |
|--------|-------|
| `RunId` | UUIDv7; for a workflow this is the same id as its output directory |
| `Mode` | `tool` or `workflow` |
| `Name` | Tool name or workflow id |
| `Version` | Workflow definition version; absent for a tool call |
| `Source` | `cli`, `chat`, or `mcp` |
| `ConversationId` | Agent conversation the job was raised for; absent for a direct call |
| `InputReference`, `OutputReference` | Image references; output is empty when the job returned data rather than an image |
| `OutputDirectory` | Artifact directory, relative to the image store root |
| `StepCount` | 1 for a tool call, step count for a workflow |
| `Success`, `Error` | A job that threw is still recorded |
| `StartTimeUtc`, `EndTimeUtc`, `DurationMs` | Wall clock |
| `StorageProvider` | Image store backing the run |
| `ArgumentsJson` | Arguments minus the image reference |
| `TraceJson` | Per-step trace; workflows only |

Timing and identity use the names from the course template's `IExperimentResult`, so the queue-driven
path can write this same shape later instead of a second table. Long strings are truncated before
write, since Table Storage caps a string property at 64 KiB and an entity at 1 MiB.

## Reading runs back

```bash
# Recent runs, newest first
dotnet run --project OcrAgent -- runs list --top 10

# Only workflow runs
dotnet run --project OcrAgent -- runs list --mode workflow

# One run in full, including the step trace
dotnet run --project OcrAgent -- runs get 019fe6ad-d532-7000-9ac4-b63ee6246386
```

The same history reaches the chat agent and MCP clients through the `ListRuns` and `GetRun` tools,
which are advertised only when a run store is configured.

Outside the application:

```bash
az storage entity query --table-name OcrRuns \
  --connection-string "$AZURE_STORAGE_CONNECTION_STRING" --num-results 10
```

## Configuration

See [CONFIGURATION.md](CONFIGURATION.md). The short version is `OCR_Runs__Provider=azuretable` plus
`AZURE_STORAGE_CONNECTION_STRING` in `.env`.

## Files

Everything new sits under `OcrAgent/Runs/`: `RunId`, `RunRecord`, `IRunStore`, `AzureTableRunStore`,
`NullRunStore`, `RunStoreConfiguration`, `RunStoreFactory`, `RunScope`, `RunRecording`,
`RecordingAIFunction`, and `RunQueryTool`. `PluginAggregator` wraps each tool once and hands the same
instances to both the agent-facing surface and the workflow engine's binding registry, so a call is
recorded once regardless of the entry point. The conversation id is set by
`OcrAgent/Agent/AgentService.cs`.
